# Security Model

## Trust boundaries

Workspace Orchestrator is local-first, but local does not mean trusted. The UI and built-in code are inside the application trust boundary. Scene JSON, imported paths and arguments, URLs, application identifiers, process output, and the local filesystem are outside it. Native operating-system APIs are trusted to enforce the current user's permissions, not to decide whether an action is desirable.

Scene definitions are untrusted input because they may be copied, downloaded, hand-edited, generated by another tool, or corrupted. Every scene is decoded with a closed action enum and validated both before persistence and before execution. Unknown action types and schema versions fail closed and surface an error.

## Process execution risks

A process runs with the user's identity and may read or change anything that user can access. A harmless-looking executable can still have dangerous arguments. Milestone 1 requires an absolute executable path and a separate argument array, checks executability and working-directory existence, captures outputs, supports timeout and cancellation, and stops the scene after failure.

Unrestricted shell strings are prohibited because quoting, interpolation, redirection, pipelines, substitutions, environment expansion, and shell startup behavior greatly increase ambiguity and injection risk. The runner never invokes `/bin/sh -c`, `/bin/bash -c`, `/bin/zsh -c`, or an equivalent wrapper. `sudo` is prohibited because orchestration should never bypass the user's normal privilege boundary.

## URL-opening risks

Opening a URL reveals it to the configured browser and may contact a remote service, expose identifiers embedded in the URL, or trigger registered protocol handlers. Milestone 1 accepts only absolute `http` and `https` URLs with a host. The UI makes URL actions inspectable before execution.

## Application-launch risks

Applications execute their own code and may restore state or access user data under their existing permissions. Launching uses the installed bundle identifier through `NSWorkspace`; scenes cannot automate application UI or AppleScript. An unknown bundle identifier fails visibly.

## Filesystem risks

Working directories and executable paths are untrusted. Relative paths are rejected. Scene storage uses one application-specific directory under Application Support and atomic replacement. Corrupt JSON is reported and never silently overwritten during a load. Milestone 1 does not request Full Disk Access.

## Log privacy

stdout, stderr, executable arguments, errors, and paths may contain private information. Milestone 1 retains the active run only in application memory and displays output for diagnosis; it does not transmit telemetry. Users should redact logs before sharing them. A future approved milestone should classify sensitive fields and apply configurable redaction before durable logging or export.

## Permissions and future approvals

Milestone 1 requests no Accessibility, microphone, camera, or administrator permissions. Future capabilities must request the narrowest permission only when a user activates the relevant feature. Risky or newly imported actions should gain an explicit preview and approval model before execution; policy decisions must remain separate from adapters.

## Distribution, signing, and notarization

The initial application targets direct macOS distribution because its long-term purpose includes orchestrating developer tools and local processes. Mac App Store sandbox constraints may conflict with those explicit user-directed capabilities. Direct distribution does not mean bypassing platform security: a release milestone must establish Developer ID signing, hardened runtime review, notarization, reproducible release procedures, provenance, and a deliberate update strategy. Milestone 1 builds an unsigned development app only.
